## Part 1 — Joint-claim rules

Notation: dependencies are labeled (a)–(l) as in the findings' §2; evidence sources are labeled A–I as in §1. I keep these distinct throughout — dependency (h) [host computer] is not Source H [MnDOT camera]; dependency (i) [calibration reference] is not Source I [battery-voltage telemetry].

**Rule 1 — MUX-level channel aggregation (covers dependency a).**
Any two or more VW/thermistor channels wired through the same multiplexer — MUX1 (16 ch., shaft 2), MUX2 (16 ch., shaft 1), MUX3 (10 ch., interior column), MUX4 (10 ch., exterior column) — must not be treated as mutually corroborating "this shaft/column's sensing is intact and its strain state is normal." The one documented real incident (a partially cut wire between a MUX and its AVW200) made only 9 of that MUX's channels unintelligible, not all of them — so a subset of plausible-looking channels on a MUX does not establish the MUX/wiring is healthy, and averaging across or discarding the "bad" channels while trusting the rest is not a valid independence argument.

**Rule 2 — AVW200-level aggregation (covers dependency b).**
The two MUXes feeding one AVW200 spectrum analyzer (up to 32 channels) must not be treated as independent of each other for "System 2's sensing chain is functioning" claims. Note: the findings do not state which two of MUX1–4 pair to which AVW200 unit, so this rule's exact scope is provisional — apply it to whichever MUX pair is confirmed to share an AVW200, not by assumption.

**Rule 3 — Per-system logger aggregation (covers dependency c).**
All streams behind one logger — CR1000/System 1 (Sources A, B, C: shaft TCs, footing TCs, CC640 camera), CR1000/System 2 (Sources D, E: VW gauges and their integrated thermistors), CR9000/System 3 (Source F: RT gauges, all shafts and columns) — must not be treated as multiple independent confirmations that "sensing at this system is intact." The logger is a storage/transmission convergence point, not a transducer: one sensor type on it reading fine (e.g., camera) does not corroborate that another type on the same logger (e.g., footing TCs) is unaffected by a logger-adjacent fault.

**Rule 4 — Per-system modem aggregation (covers dependency d).**
Simultaneous non-arrival of data from multiple sensor types within one system (e.g., TC + footing TC + camera all going quiet on System 1 at once) should be read as one Raven100 modem-link event — as actually happened (EMF-attributed loss, twice) — not as independent, coincidental sensor failures. Per the documented camera-transfer incident, a transmission failure does not imply the underlying reading was lost (the camera kept recording locally to its compact-flash card), so this is an availability/staleness failure, not a value-corruption failure, and should be diagnosed as such before treating simultaneous silence as multiple independent null results.

**Rule 5 — Conduit-bundled wiring across sources/systems (covers dependency g).**
Because TC wires and strain-gauge wires from the same shaft were bundled and pulled through the same 1.5-inch PVC conduit (2-inch for footing/columns), and Source G's (University of Minnesota) column-gauge wires were bundled with FHWA's and pulled at the same time, a claim that "the shaft's thermal record (A, or E post-Jan-2008) and the shaft's strain record (D, F) independently corroborate normal conditions" must not rest on their being on different systems/loggers as proof of independence. A single conduit-level event (crush, water intrusion) can damage wires of multiple sensor types — and both FHWA and University of Minnesota gauges — before they ever diverge onto separate MUX/logger paths. This explicitly extends to Source G even though G's downstream logger/modem/software is otherwise completely unspecified in the findings.

**Rule 6 — Host computer / analysis-software single downstream point (covers dependency h).**
Apparent cross-source agreement as displayed on the USF Geotechnical Research public website (auto-plotted via LoggerNet-adjacent scripts) must not be treated as fully corroborating that the underlying logged values are correct, because Sources A–F all converge on one host computer and one processing/plotting pipeline before display. A mislabeling, misplotting, or script bug there could make genuinely different raw readings look alike (or vice versa) without touching the raw values stored at each DAS. Any claim resting on "the website shows consistent behavior across sensor types" should be checked against raw per-logger data first. Note: Source H (MnDOT's west camera) is explicitly described as only linked from the same page, with no confirmed shared processing — this rule does not cover H.

**Rule 7 — Shared calibration reference for column loads (covers dependency i).**
Source D (VW column gauges, System 2) and Source F (RT column gauges, System 3) must not be treated as independently corroborating a "column load is within safe/design bounds" claim, because both were calibrated the same way: by correlating nominal box-section weights and false-work-reaction assumptions to measured strain. If that shared external reference is wrong, both fully hardware-independent streams would report a similarly-biased column load while both continue to look internally consistent and operational. This is the one dependency in the set that can produce a shared *systematic bias in the reported value itself*, not just an outage — hardware independence (separate MUX/AVW200/CR1000 vs. CR9000 chains) does not imply value independence here. Any claim of "two independent gauge types agree, so the column-load estimate is validated" needs the calibration assumptions checked, not just cross-system agreement.

**Rule 8 — Shared DAS-removal/scheduling event (covers dependency j).**
The simultaneous removal of all temporary DAS boxes at Pier 2 southbound for the viewing platform means every source at that pier (A–F, and G to the extent it shares the site) was unavailable for the identical non-hardware reason at the same time. This should be recorded as one project-management event, not evaluated as though each sensor type independently "went silent for its own reasons." Any claim about pier behavior during that specific window has zero corroborating sources, not "fewer" sources — and a before/after consistency comparison does not fill that gap.

**Rule 9 — Shared/unconfirmed EMF exposure (covers dependency k; hedged).**
System 1's documented EMF-attributed communication loss (twice) must not, by itself, be treated as evidence that Systems 2 and 3 were unaffected, nor assumed to have affected them equally — the findings explicitly state the source document does not address whether Systems 2/3, presumably sited nearby, experienced the same interference. An inference such as "Systems 2/3 kept transmitting cleanly, therefore the EMF effect was isolated to System 1's modem placement" should be treated as inconclusive on cross-system susceptibility, not as a confirmed independence result. This rule is precautionary/forward-looking rather than one that overturns a specific stacked claim already made in the findings.

**Rule 10 — Battery-voltage self-report rides the same channel as sensor data (covers dependency l).**
For a given system, "battery voltage reads healthy" and "sensor data is arriving and looks reasonable" must not be treated as two independent confirmations that the system is functioning correctly, because battery-voltage telemetry (Source I) travels the identical logger→modem→host pipeline as that system's sensor payload. A fault anywhere in that shared pipeline could plausibly produce a stale-but-healthy-looking battery reading riding alongside a stale or corrupted sensor reading. The battery channel cannot vouch for the sensor channel's transport integrity, since they are the same transport.

**Rule 11 — PS100 power-supply/battery-manager design flaw as a shared-design (not shared-unit) dependency (covers dependency f; heavily hedged).**
If two or more systems built to the same PS100 design each independently show the same "voltage decline toward the ~11.6 V cliff, ~8 hours remaining" signature, this should not be read as unrelated, coincidental power events that corroborate each other's normalcy — it would be one shared design limitation (can't draw from A/C and solar simultaneously without a battery-manager workaround) expressing itself on each unit's own drain schedule. Apply this rule cautiously: the findings explicitly state it is unclear whether the battery-manager fix — or even the underlying dual-source A/C-and-solar configuration that created the need for it — applies to Systems 2 and 3 at all (only System 1 is described as solar-then-A/C powered). Use this rule only if a matching decline signature is actually observed on more than one system, not preemptively.
